0. FINDINGS THAT REQUIRE AN AUTHOR DECISION BEFORE THE TABLE IS PUBLISHED
--------------------------------------------------------------------------------
These are consequences of the data, not of this step. Nothing was altered to
accommodate them.

F1 [CRITICAL — affects the central claim]
    On the held-out TEST split, "MAFF-Net (Restored)" (models/maffnet.py) achieves a
    HIGHER Dice than "MAFF-Net (Proposed)" (models/stabilized_maffnet.py) on ALL
    THREE datasets:

        dataset      Restored   Proposed   margin (Restored - Proposed)
        ISIC 2016     0.9183     0.9169     +0.0014
        ISIC 2017     0.9116     0.9096     +0.0020
        ISIC 2018     0.8844     0.8701     +0.0143

    The manuscript positions the Proposed variant as the contribution. As the
    numbers stand, it is not the strongest model in its own family by Dice, and the
    ISIC 2018 margin is an order of magnitude larger than the 2016/2017 margins.
    What the Proposed variant DOES win, consistently, is precision and specificity:

        dataset      Precision(P) Prop vs Rest    Specificity Prop vs Rest
        ISIC 2016      0.9118  vs  0.8963          0.9689  vs  0.9545
        ISIC 2017      0.9123  vs  0.9062          0.9842  vs  0.9807
        ISIC 2018      0.8669  vs  0.8719          0.9768  vs  0.9730

    i.e. the Proposed variant trades recall for precision/specificity (fewer false
    positives, more missed lesion pixels). That is a defensible and reportable
    characterisation. A claim of "best Dice" is NOT supported and must not be made.
    No single-run difference of 0.0014-0.0020 is meaningful without multi-seed
    variance, which the repository does not have (no training seed is set — Major
    finding M1, 11_Experimental_Pipeline_Audit).
    => AUTHOR DECISION REQUIRED. Not resolvable from data alone.

F2 [MAJOR] Precision is NOT measured anywhere in the repository.
    training/trainer.py::compute_metrics returns exactly six values —
    acc, dice, mIoU, sensitivity, specificity, f1. There is no precision term, and
    no metrics.json in the repository contains a precision key (verified across all
    25 metrics.json files).
    Because F1 == Dice here, precision is recoverable from the exact identity
        F1 = 2PR/(P+R)  and  F1 = Dice   =>   1/P = 2/Dice - 1/Recall
    This identity is EXACT PER BATCH. However, compute_metrics accumulates TP/FP/
    TN/FN per batch and the evaluation loop then takes a batch-size-weighted mean of
    the resulting RATIOS. A mean of ratios does not satisfy the identity, so applying
    it to the aggregated Dice and Recall yields an APPROXIMATION, not a measurement.
    Every precision value in the generated tables is therefore labelled "derived"
    (dagger footnote in .md/.tex; precision_measured=False column in .csv).
    => To make precision exact, a re-evaluation pass accumulating GLOBAL TP/FP/FN
       (rather than averaging per-batch ratios) is required. That is an evaluation
       action and was out of scope for this step. Estimated cost: well under one
       GPU-hour for all 21 runs.

F3 [MAJOR] F1 is identical to Dice by construction and is not independent evidence.
    compute_metrics defines both as 2TP/(2TP+FP+FN); the source even carries the
    comment "same as dice for binary". Verified numerically: f1 == dice to within
    1e-12 in all 21 canonical files, zero exceptions.
    Reporting Dice and F1 as two separate columns implies two independent
    measurements. Reviewers will notice. Either drop the F1 column or state the
    identity explicitly. The generated tables state it in a footnote.

F4 [MAJOR] "mIoU" is the foreground IoU, not a mean over classes.
    compute_metrics computes iou = TP/(TP+FP+FN) for the lesion class only and
    labels it mIoU. This is the standard binary-segmentation usage but the "m"
    prefix is inaccurate. Recommend reporting it as IoU, or defining it explicitly
    on first use.

F5 [MAJOR] The Paper-faithful Reconstruction rows were produced with the PLACEHOLDER
    encoder, not pretrained SAM2 weights (established in 14_Checkpoint_Verification
    §3 and restated in 15_Test_Evaluation_Report §4). Its three rows must be labelled
    accordingly wherever they appear; they are not a reproduction of the published
    MAFF-Net's reported performance and must never be presented as one.

F6 [MINOR] Protocol asymmetry, U-Net ISIC 2017. That run trained for 20 epochs; every
    other canonical run in the table trained for 40 (verified from each metrics.json
    config block). Its canonical directory is also named unet_final_2017 rather than
    unet_ISIC_2017. Disclose the epoch difference when the U-Net row is discussed.

F7 [MINOR] TransUNet ISIC 2018 diverged after its best epoch (10). The reported test
    metrics come from the retained best checkpoint and are valid (see audit 17), but
    the training curve should not be plotted without explanation.
